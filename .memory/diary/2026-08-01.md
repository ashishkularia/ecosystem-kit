## Session — acting on the hygiene findings (owner-directed)

Dear diary,

Ashish read the six hygiene reports and asked which findings belonged to the
kit, then to fix those. Three did, and all three were bugs the ecosystem found
in itself by running on itself — which is the whole thesis of this repo, so
it's worth writing down that it actually worked.

**1. health-check.sh was never refreshed into targets.** DevContainer's
hygiene run reported its health-check ERR as a false positive: the check
rejects the deliberate `$CLAUDE_PROJECT_DIR` wiring. It was a false positive
about the *wiring* but a true positive about something worse — the installed
copy dated from before the cwd fix and nothing ever replaced it, because
`install.sh` never shipped the script and `update.sh` never refreshed it. So a
bug fixed upstream weeks ago stayed red in every repo, forever. I reproduced it
exactly: copied DevContainer's actual stale copy into a scratch install → ERR=1,
85%; ran the new `update.sh` → ERR=0, 90%. health-check now installs to
`.claude/scripts/` under engine semantics.

**2. The daemon enforces rules it read at boot.** The 07-31 pr-rebase resolver
hit this live: `guard_protected_merge` blocked a legitimate feature-branch
rebase because the daemon had been up since 07-27 and the fix landed 07-29. The
resolver restarted the daemon by hand and moved on, but the pattern recurs after
every single kit update. Fixed by having the daemon compare a signature of all
`hooks/*.py` per request and retire itself on mismatch.

The instructive part was that my first version made things WORSE. I had the
daemon set a shutdown event and exit — but `cmd_start()` refuses to boot while a
live PID file exists, so the successor died on arrival while the old one was
still winding down, and the client had already burned its auto-start cooldown.
Result: no daemon at all for a full cooldown window. The end-to-end test caught
it (my unit tests were all green — they never modeled two processes). Worse, I
found a *pre-existing* race underneath: the shutdown path unconditionally
unlinks the socket and PID file, so a dying daemon happily deletes its
successor's endpoint and strands a live process nothing can reach. Both fixed by
`retire_endpoint()` — retire BEFORE replying, and only while the PID file still
names you. Lesson I want to keep: a unit test that stubs the process boundary
cannot see a handover bug; the scratch install is not optional ceremony.

**3. session_boot lied about open work.** meritick's run flagged that the banner
says "ISSUES 0 unchecked" because the counter only understands `- [ ]` and that
repo uses dated bullets. Zero is the most dangerous wrong answer here — it's
indistinguishable from a healthy repo. Real count: 39 open issues and 2 VERIFY
entries. The fallback counts per entry rather than per line, because meritick
wraps `Status: RESOLVED` onto continuation lines; I audited all 14 entries the
block-logic closes and every one is genuinely closed. Kept `PARTIALLY RESOLVED`
open, and kept the match case-sensitive so prose like "clearance not done"
doesn't close an entry.

**What I did NOT do:** the skills-clobber policy (owner picked

the single VERSION source, and kit CI. Also left every non-kit finding alone —
