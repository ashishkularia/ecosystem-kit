# DECISIONS — ecosystem-kit

- 2026-07-29 — **force-with-lease allowed, bare force never; lease-to-default-branch never.** Rebase conflict resolution needs to rewrite feature-branch history, so safe-push and guard_dangerous_commands now permit --force-with-lease/--force-if-includes (the forms that abort if the remote moved unseen). Bare --force/-f stays blocked (blind overwrite). The owner-only-main invariant is preserved by safe-push's protected-branch check running BEFORE the push — even a lease to main/master is refused. Owner asked to "allow push + force-with-lease"; the one literal deviation is that force-with-lease to main is still refused, because rewriting default-branch history would break the invariant everything else rests on.
- 2026-07-29 — **pr-rebase resolves conflicts via a headless session, not `git rebase -X`.** Blindly picking a side on a code conflict ships wrong logic; conflict resolution needs judgment + gate verification. Cheap API detection (dirty state), AI only for the actual resolve, force-push-with-lease only on green, owner still merges.
Format: `- YYYY-MM-DD — decision — why`

- 2026-08-27 — **The as-installed baseline for a project-owned file is the kit COMMIT in `.claude/kit-version`, not a new manifest.** Refreshing commands needs to tell "stale kit version" from "project customized it", and both merely differ from the current template. A hash manifest would have needed seeding, leaving all five existing repos without a baseline — the repos that actually have the problem. `update.sh` runs inside the kit repo, which has that commit's history, so `git show <commit>:templates/commands/<x>.md` reconstructs the as-installed file for free and works on every existing repo today with no migration. Every ambiguous case (no baseline, unresolvable sha, kit did not ship the file then) is treated as customized and left alone; `install.sh --force` stays the deliberate way to adopt the kit version.
- 2026-08-27 — **`mcp-audit` is a machine tool, not a kit template.** The clutter is machine-scoped: `~/.mcp.json` is an ancestor project-scope file, so with `enableAllProjectMcpServers` every server it names activates in every repo beneath it — which is why all five repos carried the same eight unused servers. Putting those names in a kit template would encode one machine's setup into every project's install. It reports only and never edits settings: disabling has per-project blast radius and no single off switch exists that would not also kill the servers in use.
- 2026-08-27 — **Both HTML and Markdown are kept for every artifact, but only one is authoritative.** They do different jobs — HTML is what you open in a browser, Markdown is what reads and diffs in a PR — so keeping one would lose a real capability. The kit is stdlib-only, so neither conversion is faithful (md→html renders a documented subset; html→md is a lossy text digest). Rather than pretend to round-trip, the *published* format is stored byte-for-byte as the source of truth and the counterpart is generated with a "do not edit" banner. Owner chose this over a metadata-only sidecar, accepting the approximation.
- 2026-08-27 — **artifact_sync is keyed on `artifact_id`, never the filename.** The same artifact republishes from the same temp path (so filename cannot distinguish artifacts) and a retitled artifact changes slug (so filename cannot identify one either). The tool response carries a stable `artifact_id`; a directory whose `artifact.json` holds it is reused. This is what turns 37 publishes into 2 directories instead of 37.
- 2026-08-27 — **Artifact commits are pathspec-scoped and auto-commit is ON by default (owner's call).** A hook committing mid-session can sweep up unrelated staged work, so the commit is `git add -- <artifact paths>` followed by `git commit -- <artifact paths>`: whatever else sits in the index is untouched. It refuses on a protected branch, on detached HEAD, and mid-merge/rebase, and never pushes. Recommendation was write-only with no commit; the owner chose auto-commit, and the scoping is what makes that safe. The staging step is not optional — on first publish every file is untracked and a bare pathspec commit fails.

- 2026-08-03 — **A reply belongs where the comment was made; an addressed thread is resolved, never silently** (owner rule). Inline review comments are answered *in their thread* — never a new review comment on the same line, which opens a second thread beside the owner's, and never a general PR comment. Conversation-tab comments have no thread (a GitHub platform limit, not a choice), so they get one general comment that quotes what it answers. The capability was already granted; only the instruction was missing, which is why the fix is mostly wording — but a granted tool nobody is told to use is not a feature.
- 2026-08-03 — **Thread resolution lives in a machine tool (`pr-thread`), not in session prompts, because it is GraphQL-only.** REST cannot resolve a review thread and no MCP tool exposes `resolveReviewThread`, so the alternative was teaching each headless session to hold the PAT and hand-write GraphQL — which breaks "Claude never handles secret values" and puts a credential in a prompt. `safe-push` is the precedent: the machine layer owns the credential and the policy, sessions call a verb.
- 2026-08-03 — **`pr-thread resolve` refuses unless a reply was posted first**, detected by the `GunAsh-` marker the poller already mints. "Reply, then resolve" was going to be a line in a prompt, and a rule that lives only in a prompt holds until the session is distracted; this makes it mechanical at no extra cost. Authorship cannot be used for the check — automated replies post under the owner's PAT, so the owner and the automation are the same author — which is exactly why the marker exists.

- 2026-08-01 — **A process another EXISTING repo could implement today belongs in the kit; the bar is a second repo, present-tense, and the question is asked ACTIVELY** (owner rule). Three candidate bars were considered and two rejected. *"True for EVERY project"* (the wording `/retro` actually shipped) is too high — it rejects the same day's self-hosted-runner guidance, which serves mylantite and meritick but not homelab or grade5. *"Could a second repo use this?"* is too vague — it invites promotion on speculation, which fills a shared kit with artifacts nobody uses and everybody must read past. The rule is therefore **present-tense and evidence-based: name the existing repo that could implement it right now, or that already has its own version.** If you cannot name one, it stays where it is; **a future need is not a reason to promote** — when that repo actually needs it, promote it then, which is the same work done with evidence instead of a prediction. Existing duplication is the strongest signal and means the promotion is *overdue*: three forked copies of `split_shell_commands` lived in this engine, only one had learned to extract `$(…)`, and the gap let a push reach a protected branch the same day. Applicability is not universality — gate a kit artifact by relevance where it is used, never by excluding it from the kit. Made operational rather than aspirational: `/retro` step 4 and `/idea` step 5 ask *which existing repo could implement this right now?* as an explicit step, and both `CLAUDE.md`s (kit + project template) carry it — a promotion rule that lives only in a diagram is noticed passively, which is the same as not at all. Genuinely project-bound things (a repo's schema, business rules, infrastructure names) stay put.

- 2026-08-01 — **Heredoc bodies are DATA and are stripped before splitting; extends the 2026-07-23 quoted-span rule.** Once newline became a separator, every line of a `git commit -F - <<'EOF' … EOF` message parsed as a command, so a commit message *about* pushing to main blocked its own commit. The opening line is still a command and is kept; the body is dropped; a real command after the terminator is still found. Correction to the same morning's "over-split, never under-split — a false positive is cheap": cheap only where the false positives actually FALL, and these fell on writing about the guards, i.e. the very next commit after changing them. Ask where a tradeoff's cost lands, not just how big it is.

- 2026-08-01 — **The kit is installed on itself by WIRING at `engine/hooks/`, never by copying the engine into `.claude/hooks/`.** Every other target gets a copy; here a copy would be a second engine that drifts from the one under active development — edit `engine/hooks/x.py` and the repo would keep enforcing the stale copy, which is exactly the bug class fixed twice on this same day (three forked command splitters that let a push through; a daemon serving pre-update hooks). `update.sh` refuses the kit repo anyway, so nothing would ever refresh that copy. This does NOT breach "copy, never symlink": that rule exists so every installed TARGET works standalone in a clone or CI, and the kit cannot be standalone from itself. Works with zero engine changes because `engine/hooks/` sits at the same depth as `.claude/hooks/`, so `PROJECT_ROOT = dirname(dirname(HOOKS_DIR))` is unchanged — `health-check.sh` therefore DERIVES the hooks directory from the wiring rather than assuming a fixed path.
- 2026-08-01 — **Anything that changes how a hook behaves belongs in `hooks_signature()`, not just hook code.** `load_kit()` memoizes per process, so an edited `.claude/kit.json` left a long-lived daemon enforcing the old gates, protected branches and source patterns. The morning's staleness check watched `hooks/*.py` only and was incomplete for exactly the reason it was written. Rule for future engine state: if a running daemon's behavior depends on a file, that file is part of the signature.

- 2026-08-01 — **Shell-command splitting is ONE implementation in `_constants.py`; no guard may define its own.** Three guards each carried a private copy and they had already drifted (40/56/40 lines — only `guard_dangerous_commands` ever learned to extract `$(…)`), which is precisely how the 2026-08-01 push bypass survived: a security parser with three forks gets fixed in one of them. Enforced by a test that fails if any `guard_*.py` re-defines `split_shell_commands`.
- 2026-08-01 — **Security splitters OVER-split, never under-split.** An extra fragment costs at most a false positive; a missed fragment is a bypass, and the guards are the last line before an owner-only action. Splitting therefore covers `&&` `||` `;` `|` `&` newline plus `(` `)` `{` `}` and backticks, and each fragment is additionally emitted with leading shell keywords (`do`, `then`), wrappers (`sudo`, `command`, `nohup`, `env`) and `VAR=value` prefixes stripped — otherwise the keyword or wrapper becomes the command word a guard inspects. MIS-splitting is not a safe form of over-splitting, so `&` stays literal after `>` (`2>&1`): a mangled `git push 2>` changes which token reads as a destination and could flip a block into an allow. Both the raw and stripped fragments are returned, because some guards match whole command lines and others inspect the first token.
- 2026-08-01 — **A local `git commit` on a protected branch stays ALLOWED; the push is the gate.** `weekly-hygiene` deliberately commits `.memory/` on the default branch and never pushes, so blocking local commits would break the kit's own automation. Pushing is what makes work shared and what the owner-only rule protects — which is exactly why the push gate having a hole was the real defect.

- 2026-08-01 — **Hook WIRING propagates as a kit-propagate policy patch, never by relaxing `update.sh`.** `update.sh` must keep its absolute never-touch guarantee on project-owned `settings.json` — that guarantee is exactly why the file is safe for a project to customize (homeassistant wires a project-local `guard_lint_md` there), and a hard rule with an exception is a soft rule. But a kit change that wires an EXISTING hook onto a NEW event then reaches installed repos as dead code: the module updates and nothing calls it. `kit-propagate` already owns this class of problem via `patch_attribution`; hook wiring joins it as a strictly ADDITIVE patch (append a missing (event, matcher, hook) triple; never remove, reorder, or touch a matcher group the template doesn't define). Corollary for reviewing kit changes: **"does this work on a fresh install" is the wrong question — the installed base is the population that matters**, so a settings-template change is not shipped until its upgrade path is verified.

- 2026-08-01 — **A diary entry is scoped to a change (branch/MR), not to a day** (owner rule; `diary_scope: "branch"` is the default). A day is an arbitrary boundary for work that spans days and interleaves with other work; a change is the unit people actually reason about and review. Keyed on the BRANCH, not the PR number, because the number doesn't exist when the work starts — which is exactly when the first entry must be written. The filename keeps a date prefix (`YYYY-MM-DD-<branch-slug>.md`, dated when the branch's diary started) so entries still sort chronologically. Falls back to the dated file on a detached HEAD or outside a git repo: a diary keyed on a branch that doesn't exist is worse than a dated one.
- 2026-08-01 — **The diary is enforced at `git commit`, not only at session end** (owner rule: "it should not wait till the end"). The Stop gate is by construction the end, so a diary it enforces is always a reconstruction; a commit is a natural checkpoint that is *not* the end, and is exactly when the reasoning is still loaded. Only `decision`/`discussion` flags gate a commit — a plain `code_change` rides to Stop — because a blocking hook that interrupts routine commits with nothing useful to say is how a guard teaches people to work around it.
- 2026-08-01 — **Docs-contract freshness compares mtimes at whole-second resolution, inclusively** (`touched_since()`). Filesystem mtime granularity is not guaranteed finer than one second, so the previous strict float comparison intermittently judged a diary written milliseconds AFTER a flag to be older and blocked correct work — and it targeted the fast path, since `/decide` now writes the diary in the same turn. A sub-second window where a just-before write counts is a rounding error; a gate that fires on correct behavior teaches people to distrust it, and this one blocks commits. Corollary: an intermittent failure in a gate's tests is a correctness report, not noise — this surfaced as a 1-in-8 flake.
- 2026-08-01 — **A matcher copied from an advisory hook into a blocking one must be re-tightened.** `guard_commit_message` detects commits with `\bgit\s+commit\b`; reusing that in the blocking pre-commit diary gate made `echo git commit` wedge an unrelated command. Blocking hooks anchor to a command boundary (start, or after `;`/`&&`/`||`/`|`/newline). Precision requirements scale with the severity of what a match triggers, so matcher reuse across severity levels is never a free refactor.

- 2026-08-01 — **A stale daemon retires itself; it never reloads in place.** `importlib.reload` cannot re-evaluate already-imported `_`-internals, so a "reload" would leave hooks half-old and half-new — worse than either. The daemon instead detects that its hook files changed, gives up its endpoint, and exits; the client direct-execs the current on-disk code for that call and boots a fresh daemon for the next one. Correctness (always the on-disk rules) beats warm-start latency for exactly one call. Rejected alternative: a watchdog thread polling mtimes — the per-request check is free, has no thread to leak, and can't fire between the check and the call it protects.
- 2026-08-01 — **A retiring daemon's cleanup is ownership-checked (PID file must still name it).** The old unconditional `unlink(SOCKET_PATH, PID_FILE)` in the shutdown path deletes whatever is at those paths — including a successor's socket, stranding a live daemon nothing can reach. Any handover between processes sharing a well-known path needs this check; it is not specific to the staleness feature (it was a latent race in every restart).
- 2026-08-01 — **`health-check.sh` is kit-owned machinery installed into every target, not a kit-repo-only script.** A check that only exists in the kit checkout cannot run from a cold clone or CI, and — worse — the copy targets *did* have was never refreshed, so a fixed-upstream bug stayed red in every repo forever. It ships to `.claude/scripts/` under engine semantics (overwrite always, refreshed by `update.sh`), which is safe precisely because it is self-contained: it reads only `TARGET_DIR`.
- 2026-08-01 — **session_boot reports drifted roster formats instead of normalizing or ignoring them.** The kit's `- [ ]` convention is right, but a counter that only understands it reports a confident **0 open** for a repo that drifted — the most dangerous possible answer, since "0 open" is exactly what a healthy repo looks like. The counter falls back to dated-bullet entries and the banner says the format drifted, so the session sees both the real count and the reason it needed a fallback. Not auto-rewriting the file is deliberate: `.memory/` is knowledge, and a hook must never silently edit it.

- 2026-07-29 — Hook wiring must be cwd-INDEPENDENT: `python3 "$CLAUDE_PROJECT_DIR/.claude/hooks/_client.py" <hook>` (supersedes the 2026-07-23 relative-wiring decision) — the relative form resolved against the shell cwd, so when a session's persistent Bash cwd drifted into a subdirectory EVERY hook failed ("can't open .../<subdir>/.claude/hooks/_client.py"); `$CLAUDE_PROJECT_DIR` is provided by Claude Code as the project root on every hook run and expands because hook commands run through a shell, keeping the portability the relative form was chosen for (no hardcoded absolute or per-machine paths) while removing the cwd dependence. Wiring-only: the engine derives its own paths from realpath(__file__). Forwarding shims that copy `_client.py` into subdirectories are rejected — they scatter dispatcher copies and paper over the bug.
- 2026-07-29 — Accessibility is compulsory in every app (owner rule): WCAG 2.1 AA is a required quality gate wired into ceremony levels (standard/full/critical), never an audit afterthought — encoded per the "owner-stated conventions become architecture tests" doctrine as an a11y gate pattern (kit.config.example.{json,md}), engineering principle §9, and MANDATORY reviewer/QA checklist passes; wherever the stack allows an executable check (eslint-plugin-jsx-a11y, axe/pa11y, template linting) the concrete command is named in the gate, and a change with no user-facing surface records N/A with justification, never a silent skip.
- 2026-07-29 — Design direction lives in-repo; the cloud artifact is a mirror (owner rule): each app keeps its canonical design-direction document in `.memory/references/design-direction*`; every design decision updates the repo doc FIRST in the same session (docs-contract style — CONVENTIONS rule + /decide step 7), and the published claude.ai artifact is regenerated FROM the repo file afterwards, never edited directly — why: account portability; the repo survives account switches, a cloud artifact does not.
- 2026-07-23 — `.memory/cache/` survives clones via a TRACKED `cache/.gitignore` (`*` + `!.gitignore`); no root-level `.memory/cache/` ignore line anywhere — a parent-dir exclude makes re-including the mechanism file impossible, so the two approaches cannot coexist. install.sh scrubs the legacy root line and seeds `.gitkeep` into empty `diary/`/`auto/` so the whole installed layout round-trips through git.
- 2026-07-23 — Daemon runtime files all share the `.daemon.` prefix (`.daemon.sock/.pid/.log/.start_attempt`) — one gitignore glob (`.claude/hooks/.daemon.*`) covers present and future runtime files; never introduce a `.daemon_*` (underscore) name.
- 2026-07-23 — guard_dangerous_commands matches filesystem/git patterns with quoted spans blanked, but SQL and env-staging patterns against the raw string — commit messages that mention `rm -rf` must pass, while `mysql -e "DELETE FROM x"` and `git add ".env"` (quoted forms are the normal shapes there) must still be caught. WHERE-less DELETE mirrors the WHERE-less UPDATE rule instead of an end-anchor a closing quote can defeat.

- 2026-07-23 — Install by COPY, never symlink — target repos must be self-contained and survive the kit repo moving, breaking, or being absent; symlinks also break in containers and on fresh clones, and hooks resolve PROJECT_ROOT via `realpath(__file__)`, which a symlink would point at the wrong repo.
- 2026-07-23 — Fail-open vs fail-closed split in `_client.py` — advisory hooks exit 0 with a stderr warning on any engine/hook crash; only `guard_dangerous_commands`, `secret_scanner`, `guard_protected_merge`, and `docs_contract` fail CLOSED (exit 2). Fixes the v1 flaw where a bug in any advisory hook blocked all tools.
- 2026-07-23 — Machinery/knowledge separation — `.claude/` holds engine+config (kit-refreshable by `update.sh`), `.memory/` holds project knowledge (never touched by updates). `CLAUDE.md` at repo root stays the auto-loaded durable-policy file and points into `.memory/`.
- 2026-07-23 — Always-loaded guarantee via `session_boot` — every SessionStart injects: STATE.md head + staleness warning, open VERIFY/ISSUES counts, newest diary tail, git branch/dirty/unpushed status, and the kit.json `always_load` list with the instruction to Read each before substantive work. The ecosystem loads regardless of task.
- 2026-07-23 — Owner-only protected branches — Claude never merges or writes to main/master in ANY repo; enforced by `guard_protected_merge` (git merge/rebase into protected, `gh pr merge`, push refspecs targeting protected, and github MCP write tools), defense-in-depth behind `~/.claude/bin/safe-push`.
- 2026-07-23 — Full SDLC ecosystem for ALL projects, including the grade5 partnership repo — everything stored in-repo (`.memory/`), per owner directive 2026-07-23.
- 2026-07-23 — Engine hook roster derived by GLOBBING the hooks dir (exclude `_`-prefixed), never a hardcoded list — adding a hook file cannot silently miss daemon registration; `health-check.sh` compares settings.json wiring against the same glob (name-token comparison, `command.split()[-1]`).
- 2026-07-23 — `kit.json` is project-owned after install — installer copies the profile only when missing; profile updates in the kit never overwrite a project's tuned `kit.json`, and `update.sh` never touches it.
- 2026-07-23 — Installer seeds `.memory/` roster ONLY where missing — knowledge is never clobbered; `install.sh` is idempotent and safe to re-run at any time. Existing `settings.json` is never overwritten either (manual-merge diff is printed instead).
- 2026-07-23 — Engine is stdlib-only Python with unittest tests — no pip installs, no venvs; hooks must run anywhere `python3` exists (pytest may not exist on hosts).
- 2026-07-23 — [SUPERSEDED 2026-07-29 by the cwd-independence decision] Hook wiring uses RELATIVE commands (`python3 .claude/hooks/_client.py <hook>`) in tracked `.claude/settings.json` only — portable across machines and clones; per-machine bits (`autoMemoryDirectory`) live in untracked `settings.local.json`.
- 2026-07-23 — jq-free tooling — all JSON work in shell scripts goes through python3 heredocs (jq is not installed on the hosts).
- 2026-07-23 — Stop-gate docs contract v2 — source edits set pending flags in `.memory/cache/pending.json`; Stop is blocked until the matching roster file (CHANGELOG/DECISIONS/diary) is newer than the flag and, when `diary: true`, today's diary entry exists. Loop-guarded via `stop_hook_active`.
